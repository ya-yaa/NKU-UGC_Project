**整体定位**

`UGC_System` 是一个“面向 UGC 图粗化实验的可视化分析系统”。它不是单纯的算法脚本集合，而是把上传数据、参数配置、流程编排、粗化执行、结果落盘、图可视化和后续 GNN 测试串成了一套完整工作流。

从架构上看，它分成 4 层：

1. Web 展示层：Flask 路由 + Jinja2 页面模板 + JS 图交互  
2. 流程编排层：`algorithms/pipeline.py` 统一调度各阶段  
3. 能力服务层：`analysis/cleaning/alpha/preprocess/calibrate/ugc` 等 service  
4. 原始算法脚本层：`scripts/UGC.py` 和 `scripts/data_process/*`、`scripts/get_alpha/*`

可以把它理解成：前端只是“壳”，`algorithms/` 是“中控层”，真正的粗化计算主体仍在 `scripts/UGC.py`。

核心目录大致是这样：

- [algorithms/pipeline.py](/f:/毕设/UGC_System/algorithms/pipeline.py:56)：统一实验流程编排器
- `algorithms/*.py`：每个阶段一个服务
- `scripts/UGC.py`：UGC 主程序，负责粗化、纯度统计、导出 coarse graph / mapping / 光谱指标 / GNN 训练
- `templates/*.html`：4 个页面
- `static/js/graph_view.js`：粗图和原图联动可视化

`outputs/` 是这个系统的核心存储区。它已经不依赖数据库，所有实验状态和结果都直接写文件。

**主流程怎么跑**

一次实验从前端提交后，主链路是：

1. 用户在上传页选数据集和参数
2. `app.py` 创建 `run_id`，把初始状态写入 `outputs/<run_id>/state.json`
3. 后台线程调用 `UGCPipeline.run()`
4. `pipeline.py` 顺序执行：
   - 数据分析
   - 数据清洗
   - alpha 计算
   - 预处理
   - bin width 标定
   - UGC 粗化
5. `scripts/UGC.py` 在粗化时直接把 coarse graph、mapping、导出文件、谱指标、纯度统计写进 `outputs/<run_id>/`
6. 结果页直接读取这些 JSON/PT/TXT 文件展示

对应代码主入口在 [app.py](/f:/毕设/UGC_System/app.py:162) 和 [pipeline.py](/f:/毕设/UGC_System/algorithms/pipeline.py:66)。

`run()` 的逻辑非常清晰：

**各 service 文件功能**

[analysis_service.py](/f:/毕设/UGC_System/algorithms/analysis_service.py:25)  
负责读取原始或 processed 数据，分析节点数、边数、平均度、最大度、特征维度、标签类型、标签维度。它的作用主要是给运行页展示数据概况，也帮助判断单标签/多标签。

[cleaning_service.py](/f:/毕设/UGC_System/algorithms/cleaning_service.py:25)  
负责数据清洗。对原始数据会：
- 只保留有标签节点
- 重映射节点 ID 为连续编号
- 去掉重复边
- 同步切片特征矩阵  
清洗结果会写到 `outputs/<run_id>/_working_data/<dataset>/raw/`。这一步很重要，因为后续 alpha 和预处理都基于“清洗后的数据”跑。

[alpha_service.py](/f:/毕设/UGC_System/algorithms/alpha_service.py:20)  
负责根据策略 `v1/v2/v3/v4` 动态加载 `scripts/get_alpha/*.py`，计算异配系数 alpha。  
4 种策略分别对应：
- `v1` 第一标签
- `v2` 标签集合交集
- `v3` 标签位置对齐
- `v4` Jaccard 阈值

[preprocess_service.py](/f:/毕设/UGC_System/algorithms/preprocess_service.py:27)  
负责调用 `scripts/data_process/data_process1~4.py`，把原始文本/npz 数据转成 UGC 脚本可直接使用的：
- `edge_index.pt`
- `node_feat.pt`
- `label.pt`

[calibrate_service.py](/f:/毕设/UGC_System/algorithms/calibrate_service.py:21)  
负责“桶宽标定”。本质上是不断调用 `scripts/UGC.py --coarsen_only True --bin_width x`，从 stdout 里解析 `Graph reduced by: ... percent`，通过二分搜索找到最接近目标压缩率的 `bin_width`。

[ugc_service.py](/f:/毕设/UGC_System/algorithms/ugc_service.py:34)  
是对 `scripts/UGC.py` 的命令行封装器。它不自己做算法，而是：
- 拼命令参数
- 调用 UGC 脚本
- 从 stdout 里解析压缩率、supernode 数、accuracy、macro-F1、时间
- 检查是否生成了 `coarse_graph.json`、`exports/`、`metadata.json` 等文件

**脚本层：真正干活的是 `scripts/UGC.py`**

[scripts/UGC.py](/f:/毕设/UGC_System/scripts/UGC.py:67) 是最核心的算法文件。

它做的事可以概括为：

1. 解析参数：数据路径、alpha、bin_width、模型、压缩率、是否只粗化、是否计算谱误差等
2. 构造增强特征：把原始特征和邻接结构按 alpha 融合
3. 通过随机投影 + LSH 分桶生成 supernode
4. 可选地对“低纯度且成员数较多”的 bad supernode 做局部二分 KMeans 拆分
5. 聚合 coarse feature、coarse adjacency、coarse labels
6. 计算 purity、谱误差等指标
7. 保存所有前端需要的 JSON/PT/TXT 导出
8. 如果不是 `coarsen_only`，继续训练 GCN/GAT/GIN/SAGE/APPNP/3WL 等模型

你论文里特别关心的几个增强点，在这里都能看到：

- supernode purity 统计：[UGC.py:197](/f:/毕设/UGC_System/scripts/UGC.py:197)
- 相似度加权特征聚合：[UGC.py:242](/f:/毕设/UGC_System/scripts/UGC.py:242)
- bad supernode 局部 KMeans 拆分：[UGC.py:304](/f:/毕设/UGC_System/scripts/UGC.py:304)
- 导出 coarse_graph / mapping / metadata：[UGC.py:397](/f:/毕设/UGC_System/scripts/UGC.py:397)
- 粗化主过程打印压缩率：[UGC.py:1347](/f:/毕设/UGC_System/scripts/UGC.py:1347)
- `coarsen_only=True` 跳过训练：[UGC.py:1637](/f:/毕设/UGC_System/scripts/UGC.py:1637)

也就是说，这个系统不是简单“调用原版 UGC”，而是在原始 UGC 上叠加了面向你课题的几个改进和导出能力。

**前端交互核心：`graph_view.js`**

[graph_view.js](/f:/毕设/UGC_System/static/js/graph_view.js:1) 负责结果页的双图联动。

它的工作流程是：

- 读取后端给的 `graph_preview = coarse_graph.json`
- 用 Cytoscape 渲染 coarse graph
- 按边权只显示前 N% 边，避免图太乱
- 点击 coarse supernode 时，请求 `/mapping/node/<supernode_id>`
- 点击 coarse edge 时，请求 `/mapping/edge/<edge_id>`
- 在右侧渲染原图局部子图，并支持反向高亮

这就是为什么系统结果页能做到：
“点一个 supernode，看它由哪些原始节点组成；点一条粗边，看它对应哪些跨簇原始边”。

**输出文件分别有什么用**

每次实验都会落到 `outputs/<run_id>/`，里面常见文件作用如下：

- `state.json`：运行中状态，给运行页轮询
- `summary.json`：实验总摘要，结果页主数据源
- `coarse_graph.json`：粗图节点、边、详情、纯度、可视化元信息
- `mapping.json`：原图到粗图的节点/边映射子图
- `metadata.json`：导出目录、参数、统计信息
- `purity_stats.json`：supernode purity 统计
- `spectral_metrics.json`：谱误差、Dirichlet energy、hyperbolic error
- `supernode_members.json`：supernode -> 原始节点列表
- `exports/pt/`：PyTorch 格式的粗图
- `exports/text/`：文本格式的粗图
- `gnn_tests/*.json`：后续不同模型的测试记录

前端尤其依赖两个文件：

- `coarse_graph.json`
- `mapping.json`

这个设计非常好，原因是前后端解耦很彻底，页面只认结果文件，不需要重新推导。
